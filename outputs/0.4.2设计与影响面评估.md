## 1. 逐条核实

| # | 来源①的建议 | 核实结论 | 是否库侧 |
|---|---|---|---|
| 1 | `is_oos` 可行性下界没提示（默认约需 43 期） | **成立**，但**根因更深**：是 `embargo` 的**单位错配**（见 §1.1） | ✅ |
| 2 | `double_sort` 缺收益列时，报错指向下游 `ic` 层 | **成立**（复现一致） | ✅ |
| 3 | `clean()` 的"一次只能一列"没在参数说明里点明 | **成立** | ✅ |
| 4 | `to_markdown()` 未声明 `tabulate` 可选依赖 | ❌ **不成立** —— 库自带渲染，零 tabulate 依赖（见 §1.4 的决定性实验） | ❌ 无需改代码 |
| 5 | 节号自动编号但缺稳定"节定位"入口 | **成立**（0.4.0 的自动编号是它的根因） | ✅ |

### 1.1 第 1 条的根因：`embargo` 数的是"位置"，`build_report` 给的是"交易日"

`split_is_oos(dates, …, embargo=N)` 里的 `N` 是**在 `dates` 里数多少期**；
而 `build_report` 的默认值是 `max(horizons) + 1` —— `horizons` 是**交易日数**。
日频面板上两者恰好同量纲；**月末调仓就差约 21 倍**。

月末 60 期面板实测（0.4.1）：

| horizons | 默认 embargo | 结果 |
|---|---|---|
| `(5,)` | 6 | 跑通，IS=35 / OOS=18 |
| `(21,)` | 22 | 跑通，但**挖掉 22 个月末 ≈ 2 年**（本意是 22 个交易日 ≈ 1 个月） |
| `(21,63)` | 64 | ✗ **样本内 0 期**（`split/too_few_periods`） |
| `(21,63,126)` | 127 | ✗ 同上 |
| 显式 `embargo=1/2` | — | 跑通（用户只能自己绕开默认） |

来源①说的"默认约需 43 期"正是 `0.7N − 22 ≥ 8 ⇒ N ≥ 43` 那一行 ✓ 算式吻合；
它还补了一个我没想到的观察：**`ratio` 的可行区间很窄**（N=60 时约 0.50~0.87，
N=80 时约 0.38~0.90）—— 提高 `ratio` 会把样本外压到 8 期以下，两头互相挤。

**危害**：非日频面板上默认配置要么**过量 purge**、要么**直接跑不起来** ——
比"少个提示"严重，属真 bug。

### 1.2 第 2 条复现（与来源①一致）

保留 `factor` 但切掉收益列时，报错来自更下游：

```
[ic] 违反契约 `no_returns`
数据里没有 `forward_return_*` 列；先跑 forward_returns() 与 clean()。
```

错误码指向 **`ic` 层**，而问题在 `double_sort` 的入参 —— 排查时容易误判成"没跑 forward_returns"。

### 1.3 第 3 条复现（与来源①一致）

```python
acna.clean(multi_factor_df, ret)
# [clean] ambiguous_factor：因子表看不出哪列是因子值（候选 ['roe','mom']）。
#          修法：把列命名为 `value` 或 `factor`。
```

行为正确（库不该猜），但"**一次只能一个因子**"这件事没在任何参数说明里点明。

### 1.4 第 4 条：**核实为误判**（附决定性实验）

来源①称「`to_markdown()` 内部走 `pandas.DataFrame.to_markdown()`，需要 `tabulate`」。
核实证据（三条，互相独立）：

1. **代码**：全库 `to_markdown` 只出现 4 处 —— `Report.to_markdown`（定义）、
   它调用自己（存盘 `save`）、docstring 示例、`HealthReport.to_markdown`。
   **没有任何一处调用 pandas 的 `DataFrame.to_markdown()`**。
   来源①引用的 `report/__init__.py:160` 正是**库自己那个方法的 def 行**。
2. **实现**：`_md_table()` 是**手写渲染器**（自己拼 `| … |` 与分隔行，值走 `_fmt()`），
   不经过 pandas 的渲染入口。
3. **决定性实验**：用 stub 屏蔽 `tabulate` 后（`import tabulate` 直接抛 ImportError），
   `Report.to_markdown()` 正常输出 **6099 字符 / 13 节**，
   `HealthReport.to_markdown()` 正常输出 2071 字符。

→ 来源①观察到的 `ImportError` 来自**它自己脚本**里的 `DataFrame.to_markdown()`
（会话里也提到"我改自写表格"），不是库的缺陷。
**结论：库侧不需要捕获这个异常、也不需要声明 `tabulate` 依赖** ——
否则会误导使用者去装一个本库不需要的包。
唯一值得做的是**一句文档澄清**（因为两个方法同名，太容易混）。

## 2. 统一后的修改建议（5 项）

### A. `is_oos` 的 purge 改成**按日历精确剔除**（核心，修 1 的根因）

```python
split_is_oos(dates, *, ratio=0.7, cut=None, embargo=0, min_periods=8,
             calendar=None, purge_horizons=None, entry_lag=1)
```

- 给 `calendar` + `purge_horizons` → **精确 purge**：剔掉"出场日 ≥ 切分日"的样本内样本
  （返回多 `purged` 与 `mode='exact'`）；
- 只给 `embargo` → 保持"按位置数"语义，**但文档要把单位写对**（分析日期**期数**，不是交易日
  —— 现在这点是反的）；
- 两者同时给 → 报错（避免两种口径打架）；
- `entry_lag` **从 `ReturnModel` 取**（`entry='close'` 时是 0，硬编码 1 会又差一天）；
- `build_report(is_oos=…)` 默认改走精确 purge。

**并把来源①的两条提示一起做掉**：docstring 写下界
`N ≳ embargo + 2×min_periods`（精确模式下是"所需 purge 期数 + 2×min_periods"），
报错里再算一行**可行区间**，例如
`可行 ratio 约 [0.50, 0.87]（N=60, embargo=22, min_periods=8）` ✓。

### B. 两条报错改成"指向下一步"（修 2、3）

| 位置 | 现在 | 改成 |
|---|---|---|
| `double_sort` / `grouped_ic` 缺收益列 | 抛到下游 → `[ic] no_returns` | 入口自检：`group/missing_returns`，文案给两步处方（`forward_returns` → `clean` → `double_sort(cr.data, by=…)`）并点明"只切 `['factor']` 会掉收益列" |
| `clean` 的 `ambiguous_factor` | 只说"改列名" | 追加"**本库一次分析一个因子**；多列宽表请显式指定要用的列；多因子比较用 `factor_correlation` / `redundancy_check`" |
| `clean()` / `build_report()` 的 `factor` 参数说明 | 未点明单列约束 | 加一句"一次只接受一个因子；多因子请逐列调用或先合成" |

### C. 文档澄清 `to_markdown` 的依赖（修 4 的**唯一**合理动作）

在 README 与 `docs/输入数据规格.md` 各加一句：

> `Report.to_markdown()` 自带 Markdown 渲染，**不依赖任何可选包**。
> 需要 `tabulate` 的是 **pandas 自己的** `DataFrame.to_markdown()` —— 两者同名但不是一回事。

**明确不做**：不加 `try/except ImportError`、不声明 `tabulate` 依赖（见 §1.4）。

### D. 报告节次的稳定定位入口（修 5）

```python
SECTION_KEYS = ('verdict', 'health', 'ledger', 'ic', 'newey_west', 'quantile',
                'portfolio', 'stability', 'tail', 'turnover', 'is_oos', 'dropped')

Report.sections() -> list[dict]   # [{'key':'quantile','number':'六','title':'分层'}, …]
```

下游改判 `key`，不再硬编码 `## 七` ✓；并在 `to_markdown` 的 docstring 加一句
**"节号是自动编号、会随版本变化，请勿按节号解析"** ✓。

### E. 契约类 docstring 点明"入口层会补校验"（修 6，可选）

在 `FactorPanel` / `PricePanel` / `Universe` / `Tradability` / `Grouping` / `Exposures` /
`Events` 的 docstring 各加一句：**"`build_report` / `check_parity` 会在入口处补校验；
传裸 DataFrame 也会被自动包装并校验"** —— 让"我传的是裸表"的人知道校验已经发生。
成本极低，建议顺手做。

## 4. 验收清单

1. 月末 60 期 + `horizons=(21,63,126)` + `is_oos=0.7` → **跑通**，且 IS 段**每个样本**的
   出场日**严格早于**切分日（按日历验算，不断言魔数）；
2. 日频面板：新实现与 0.4.1 的段边界差异 **≤ 1 期**（A/B 证明"只修了单位错配"）；
3. `entry='close'` + `is_oos` → purge 少一天（与 `model` 一致）；
4. `double_sort(缺收益列的 panel)` → `group/missing_returns` 且文案含两步处方；
   `clean(两列因子)` → 文案含"一次分析一个因子"；
5. **屏蔽 `tabulate`** 后 `Report.to_markdown()` / `HealthReport.to_markdown()` 仍正常
   （用 stub 验证；这条同时防止将来有人误引入 tabulate 依赖）；
6. `Report.sections()` 返回的 `key` 稳定（加一节后旧 key 仍指向同一节）；
7. 全量测试 + CI 等价环境 + 与 0.4.1 的 A/B：**除 `is_oos` 那两段外，其它数字逐位不变**。

## 5. 需要拍板的两件事

1. **A 的默认行为变更**：`build_report(is_oos=…)` 默认改走精确 purge →
   已用 `is_oos` 的人那两段统计会变（修 bug 的必然）。接受吗？
2. **E 做不做**（契约 docstring 补一句）—— 成本极低，我建议做；不做也不影响其它四项。
