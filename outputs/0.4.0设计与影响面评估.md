## 0.5 契约层补口（来自用户反馈，**已逐条实测**）

> 反馈两条 + 两条次要缺口。**结论：全部属实**，且实测发现两处比反馈描述的更严重。
> 性质上这是 **0.3.0「入口层收口」的补完** —— 0.3.0 声称收口了防线 1，
> 但 `groupby`/`exposures` 并未进边界，`_check_finite` 也只覆盖声明了 `numeric` 的契约。

### 0.5.1 反馈 ①：`build_report` 的可选契约传参没补全 —— **属实**

实测：`build_report` 调 `ensure_contract` 时只传了 `factor / prices / calendar / universe`；
`groupby`、`exposures` **没有进边界**；而 `build_report` 也没有 `tradability` 入参
（用户想自带可成交性，只能往 prices 里塞 `can_buy_open` 列 —— 隐式、且没有校验）。

### 0.5.2 反馈 ②：`inf` 口径不一致 —— **属实，范围比反馈更大**

机制：`_Panel._check_finite()` 只遍历 `self.numeric`；声明 `numeric = ()` 的契约
**一个列都不查**。实测同一个 `inf`：

| 契约 | `numeric` 声明 | 实测 |
|---|---|---|
| `PricePanel` | 全部价格列 | ✓ 拦下 `non_finite` |
| `FactorPanel` | `('value',)` | ✓ 拦下 `non_finite` |
| `Tradability` | 3 列 | ✓ 拦下 `non_finite` |
| **`Exposures`** | `()` | **★ 放行** |
| **`Universe`** | `()` | **★ 放行**（额外数值列含 inf） |
| **`Grouping`** | `()` | **★ 放行**（额外数值列含 inf） |
| **`Events`** | `()` | **★ 放行** |

★ 反馈只点了 `Exposures`，实际是 **4 个契约**（凡未声明 `numeric` 的）。

**危害实测（比预想的更微妙）**：把 `inf` 塞进 `exposures` 再走
`build_report(..., exposures=…, preprocess=('neutralize',))` → **跑通**，
且结果与把那个 `inf` 换成 `NaN` **逐位相同**（`p_adj=0.2735009315021386`、`net=0.10513`）。
即 `inf` 被**静默当成缺失**处理了 —— 不是"算出垃圾"，而是"**用户拿不到任何信号**"。
而本库的立场就写在 `_check_finite` 自己的 docstring 里：「NaN 是合法缺失，inf 不是」。

### 0.5.3 次要缺口一：`groupby` 形状不对时漏**裸异常**，且指向错层 —— **属实，且更糟**

反馈说"要到下游 `preprocess`/`neutralize` 才报错（错误信息指向错层）"，实测是**裸异常**：

| 误用 | 实测结果 |
|---|---|
| `build_report(groupby='industry')`（字符串） | **★ `AttributeError: 'str' object has no attribute 'iloc'`** |
| `build_report(groupby=空表)` | **★ `IndexError: single positional indexer is out-of-bounds`** |
| `neutralize(factor, groups='industry')` | **★ `AttributeError: 'str' object has no attribute 'reindex'`** |

这与 0.3.0 已修好的 `factor=None` / `prices=None` / `calendar=None` / `factor=42`
是**同一类问题**，只是当时没覆盖 `groupby`/`exposures`。

### 0.5.4 次要缺口二：`events` / `tradability` 未进入口校验 —— **部分属实**

- `ensure_contract(events=…)` **是校验的** ✓（缺 `event_type` → `Events/missing_columns`）。
- 但 `align_event_windows(prices, events, calendar, …)` 只做 `ev = _as_df(events)`，
  **不包装、不校验** ✗ —— 它才是 events 的真正入口。
- `build_report` 没有 `tradability` 参数（见 0.5.1）。

### 0.5.5 修法设计（建议并入 0.4.0，且**排在 D 之前**）

| # | 改动 | 设计要点 |
|---|---|---|
| F1 | `_check_finite` 改为遍历「`self.numeric` ∪ **所有数值 dtype 列**」 | 不再依赖契约是否声明 `numeric`；标签 / bool 列天然跳过。`numeric`（不得 NaN）与 finite（不得 inf）语义分开保留 |
| F2 | `build_report` 把 `exposures` 送进边界（按 `Exposures` 包装） | `Exposures.required = ()` 只要求非空 → **无误伤风险**；配合 F1 一并拦住 inf |
| F3 | `groupby` 送进边界 | ⚠️ `Grouping.required = ('group',)` 会把"列名叫 industry"的合法用法拒掉 → 建议把 `Grouping` 放宽为「**恰好一列**（或名为 `group` 的那一列）」；`neutralize` 本来也只接受单列分组 |
| F4 | `build_report` 新增 `tradability=None` 入参 | 给了就按 `Tradability` 校验并**跳过自动计算**（现在是隐式塞列）；`prepare_tradability` 语义不变 |
| F5 | `align_event_windows` 用 `ensure_contract` 包装 `events` | 三行；错误从此指向 `Events` 而不是下游 |
| F6 | `events` **不加进** `build_report` | 它不做事件研究（那是 `align_event_windows` 的活）→ 加了反而误导；文档写明边界 |

**为什么排在 D 之前**：D（分组 IC / 双重排序）要新增 `by` / `groupby` 入参 ——
如果边界不先补，新功能会**继承同一批裸异常与错层报错**。

**影响面**：F1 会让"以前带 inf 能跑通的面板"开始被拒（**有意为之**，属破坏性收紧 →
与 0.3.0 同类）；F2–F5 是把已有能力接到边界上；F6 只是文档。全部落在 **0.4.0**，
并且需要新的一轮"不改数字"的 A/B（合法数据必须逐位不变）。

## 1. A. 因子相关性 / 冗余度检验（补文章第 6 步）

### 1.1 API 设计

```python
factor_correlation(factors, *, method='spearman', min_overlap=20) -> FactorCorrResult
    # factors: Mapping[str, FactorPanel|DataFrame|Series]，或一个多列 DataFrame
    # 返回：相关性矩阵（每对因子的逐期截面相关汇总）+ 每对的期数与重叠样本量

redundancy_check(candidate, library, *, threshold=0.7, method='spearman',
                 min_overlap=20) -> RedundancyResult
    # candidate: 待入库因子；library: 因子库（同 factor_correlation 的入参）
    # 返回：是否冗余 + 最相关的几个因子 + 相关性 + 重叠期数 + 阈值依据
```

### 1.2 三个必须定死的语义（否则数字不可比）

1. **逐期截面相关，再对时间汇总**，**不做整体池化相关**。
   池化会把"因子间共同的时间漂移"混进来，系统性**高估**相关性 → 会把互补因子误判成冗余。
   汇总给 `mean` / `median` / `positive_rate`（逐期为正的比例）/ `n_periods` 四个数，
   判定用 `mean`（可配 `median`），并把用哪个写进结论。
2. **重叠不足时给 NaN + 原因**，不静默。`min_overlap` 期以下不出相关性数字，
   `RedundancyResult` 里写明"哪几对因子重叠不足、还差多少期"。
3. **判定要给依据**（与 `Verdict` 同风格）：`非常冗余（|ρ|=0.82 ≥ 阈值 0.7，最相关：ROE_TTM，重叠 58 期）`。

### 1.3 影响面

| 维度 | 评估 |
|---|---|
| 默认行为 | **无影响**：纯只读函数，`build_report` 默认不接（只在显式传 `library=` 时才加一节） |
| 现有数字 | 不变（不参与 `build_report` 的默认流水线） |
| API 面 | `__all__` 106 → **108**（`factor_correlation` / `redundancy_check`）；`test_api_surface` 的 PROMISED 是否加：**建议加** |
| 性能 | O(N² · 期数 · 截面)。实现走"按日分组 → rank → 矩阵化相关"，40 因子 × 240 期 × 800 只应在**秒级**；实施时给基准并进 CI 护栏 |
| 测试 | ① 与手工 pandas 逐日 rank 相关**逐位相同**；② 重叠不足 → NaN + 原因；③ 已知答案（构造两个完全相同的因子 → ρ=1、判为冗余；正交两个 → 判为非冗余） |
| 文档 | 新 API 的 docstring + `docs/输入数据规格.md` 不需要动；CHANGELOG `### 新增` |

## 2. B. 样本内外拆分（补文章第 5 步）

### 2.1 API 设计

```python
split_is_oos(dates, *, ratio=0.7, embargo=0) -> dict   # {'is': Index, 'oos': Index, 'cut': Timestamp}
```

### 2.2 两个专业细节（文章没提，我们补上）

1. **时序数据不能随机切** —— 必须按时间顺序切。随机切会让相邻期的重叠收益跨到两边，
   直接把"样本外"变成"样本内的近似复制"。这条要写进 docstring 与文档。
2. **切分点泄漏（lookahead across the cut）** —— 持有期 `h` 的样本其前向收益**跨过切分点**，
   等于让样本内"看到"样本外的价格。设计给 `embargo`/`purge`：
   `IS` 尾部去掉最后 `h` 期（按持有期长度），`OOS` 从切分点起算。
   → 报告里明写用的是哪种切法，不让人猜。

### 2.3 影响面

| 维度 | 评估 |
|---|---|
| 默认行为 | **无影响**：`build_report` 不自动切分（切分是研究决策，不该库替你定） |
| 报告 | **新增一节**「样本内 / 样本外对照」：两段的 IC / IR / 胜率 / 分层单调性并排 + 有效样本量提示（OOS 期数少时不要过度解读） |
| 触发方式 | 只有显式传 `is_oos=('2024-01-01', None)` 这类参数才加该节 → **默认报告不变** |
| API 面 | +1 |
| 测试 | ① 期数正确、顺序切；② **构造一个会泄漏的样本，验证 purge 后 IC 变化方向符合预期**；③ `ratio`/`embargo` 的边界（期数不足 → 报错而不是静默给空段） |

**「组合绩效（统计口径，非可交易净值）」**，并在节内注明已扣成本（`net` 口径）与未模拟的部分。

## 4. 两个既有待办的归位判断

### 4.1 D. 分组 IC / 双重排序 —— **建议同批，与 A 共骨架**

⚠️ 先说一个对不上的地方：CHANGELOG 里写"触发条件见 `outputs/功能增补清单`"，
但那份清单里**没有"分组 IC"字样**；它写的是**双重排序**：

> 独立双重排序（先按规模分 5 组，**组内**再按 ROE 分 5 组）／条件双重排序（每组内独立分位）
> 输出：25 宫格平均收益热力图 + 组内单调性检验
> 可证伪的预测：若 ROE 只是规模代理，则**在同一规模组内** ROE 的单调性应该消失。

所以待办的真实内容应是「**分组 IC + 组内一致性 + 双重排序网格**」。设计按这个口径走：

```python
grouped_ic(data, *, by, horizons=None, method='spearman', min_group_size=5)
    # 逐期、**组内**截面 IC → 汇总；组内样本不足则该期该组跳过并记账
group_consistency(grouped, *, horizons=None)
    # 各组 IC 的**同号比例**与离散度；回答"因子是不是只在某一组里有效"
double_sort(data, *, by, n_by=5, n=5, method='independent', horizons=None)
    # 25 宫格（by × q）平均收益 + 组内单调性
```

**为什么建议同批**：A（相关性）与 D（分组 IC）共用同一条骨架
「**按列分组 → 逐期截面统计 → 时间汇总**」；分两批做会长出两套写法（本库最怕"同一件事两种口径"）。

**验收判据（独立于 A）**：
- 25 宫格单元格数 = `n_by × n_q`（缺格要记账）
- **组内 IC 的样本加权和 = 全局 IC**（无缺失时应逐位相等）—— 这条是分组 IC 的正确性锚
- 组内单调性：与 `quantile_stats.monotonicity` 同口径

**影响面**：API +3；报告默认**不加节**（分组要显式给 `groupby`），给了 `groupby` 时可自动加一节 → 二选一，我倾向"给了就加"（否则用户不知道自己漏看了什么）。

### 4.2 E. 退市收益约定的行业维度复核 —— **建议独立、不占代码批次**

**性质不同**：这是**案例复核**（验证"退市结论是否被行业结构驱动"），产出应是
`outputs/退市收益约定_行业维度复核.md`，而不是库 API。

**数据可行性：已验证可行**。`verify_roe_neutral.py::load_industry` 已有申万 L1 的
**as-of 取法**（`data/sw_industry/members.parquet` 带 `in_date`/`out_date`），
且脚本注释已经写明关键纪律：

> 比"最新快照"正确：行业分类会变，用今天的行业去解释 2019 年的股票是前视。

**建议的复核内容**：按申万 L1 分层，看三种退市约定（`nan` / `last_price` / `haircut`）
对 RankIC 与腰斩率的影响**是否集中在少数行业**；若集中，则回看结论是否该限定适用范围。
**只有当复核指向"库的口径需要改"时，才回流成代码改动**（届时按破坏性变更走 minor）。

→ 因此：**不并入 0.4.0 代码批次**，作为独立案例任务并行。
