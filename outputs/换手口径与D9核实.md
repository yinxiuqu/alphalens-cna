> 数据：真实 ROE 月度面板，91 个调仓日 × 5,004 只股票，清洗后 343,245 行。
> 复现：`python verify_turnover.py`（复用 `accept_m0.py` 的加载逻辑）
> 原始数字：`outputs/turnover_check.json`
> 日期：2026-07（M1 阶段 · 对拍层收尾）

## 一、为什么要核实

M1 的对拍层要求"换手率与 alphalens 逐位一致"。第一次对拍**没过**：

```
❌ 换手   最大差 5.000e-01   (容差 1e-10, 比对 640 点)
   最大差出现在第 24 个点：本库 0.5 vs alphalens 1
```

差 0.5 —— 不是精度问题，是**定义不同**。查 alphalens 源码
（`alphalens/performance.py::quantile_turnover`）：

```python
quant_names = quantile_factor[quantile_factor == quantile]
quant_name_sets = (quant_names.groupby(level=["date"])
                   .apply(lambda x: set(x.index.get_level_values("asset"))))
new_names = (quant_name_sets - quant_name_sets.shift(periods=period)).dropna()
quant_turnover = new_names.apply(f) / quant_name_sets.apply(g)   # f=len, g=len
```

即 **单边口径**：

```
tau_t = |Q_t \ Q_{t-1}| / |Q_t|
```

分子只数**新进**、不数退出；分母是**本期**名单。名单完全换血 → 1.0。

本库原来用的是**对称口径**：

```
tau_t = |Q_t △ Q_{t-1}| / |Q_t ∪ Q_{t-1}| / 2
```

进出都数、除以并集。名单完全换血 → **0.5**。差的这 0.5 就是这么来的。

## 二、两种口径的实测差距（真实数据）

| 分位 | alphalens 口径（默认） | symmetric 口径 | 差 |
|---|---|---|---|
| Q1 | 10.35% | 8.30% | +2.05pp |
| Q2 | 19.76% | 14.08% | +5.68pp |
| Q3 | 25.85% | 17.34% | +8.51pp |
| Q4 | 26.71% | 17.76% | +8.95pp |
| Q5 | 17.50% | 12.82% | +4.69pp |
| **平均** | **20.03%** | **14.06%** | **+5.97pp** |

规律：**名单规模变化越大，两者差得越多**。Q4 名单膨胀（有新进没退出）时
alphalens 口径高估、symmetric 口径被并集摊薄。进出对称时两者相同
（已由 `tests/test_analysis.py::test_turnover_*` 钉住）。

**决定（D11）**：默认改为 alphalens 口径（`method='alphalens'`），
因为它①是文献标准口径、②能守住"取代 alphalens"的承诺；
`symmetric` 保留为可选（`method='symmetric'`），用于名单规模剧变时的稳健估计。
非法 `method` 直接报 `ContractError`，不静默换口径。

## 四、D9 的真相：不是返 NaN，是**跑不起来**

之前记录 D9 为"非日频下静默返回全 NaN"。实测**低估了严重程度**。

同一份月频面板喂给 alphalens：

```
ValueError: Inferred frequency None from passed values does not conform
            to passed frequency C
  File "alphalens/utils.py", line 846, in get_clean_factor_and_forward_returns
  File "alphalens/utils.py", line 358, in compute_forward_returns
    df.index.levels[0].freq = freq
  File "pandas/core/indexes/datetimelike.py", line 106, in freq
```

**崩在清洗阶段**，不是计算结果阶段。`alphalens/utils.py:358` 把频率
**硬写**到因子日期索引上；真实 A 股月频日期（每月最后一个交易日）不落在
任何规则频率网格里，pandas 直接拒绝。

### 触发条件（精确）

| 因子日期索引 | alphalens 行为 |
|---|---|
| 日频（`freq='B'`） | ✅ 正常 |
| 规则月末（`freq='ME'`，人造） | ✅ 正常 —— 对拍测试就是用这个验证月频逻辑 |
| **不规则月频**（`freq is None`，**真实 A 股**） | ❌ **清洗阶段抛 ValueError** |

也就是说：**alphalens 在它最主要的应用场景（月频因子分析）上根本不能用**。
这不是"某个函数有 bug"，是整条链路的设计假设（"日期索引必有 freq"）不成立。
本库完全不依赖 `freq` —— 两个量在同一份面板上分别得到
**秩自相关 0.9227**（79 期全有值）与 **月换手 20.03%**。

**决定（D12）**：`check_parity` 捕获 alphalens 一侧的异常，转成
"无法对拍"的检查结果并如实说明，**不漏第三方堆栈**；但本库自己的
`ContractError` 照常抛出（那是我们的 bug，必须炸）。

## 五、对拍层的最终状态

同一份合成日频面板（150 天 × 50 只，h=1/5/21，5 分层）：

```
与 alphalens 等价性回归（退化场景：日频 + 收盘成交 + 关 A 股规则）
  样本：本库 6,450 / alphalens 6,450
  ✅ IC             最大差 0.000e+00    (容差 1e-10, 比对 387 点)
  ✅ 分层均值           最大差 0.000e+00    (容差 1e-10, 比对 1,935 点)
  ✅ 换手             最大差 0.000e+00    (容差 1e-10, 比对 640 点)
  结论：✅ 通过
```

**三个量、2,962 个比对点，最大差恰好 0.0 —— 逐位相同，不是"接近"。**
样本数也一模一样（6,450 / 6,450），说明清洗规则丢的行都完全一致。
这是"取代 alphalens"这句话唯一的硬证据，由 `tests/test_compat.py`（12 个测试）守住。
