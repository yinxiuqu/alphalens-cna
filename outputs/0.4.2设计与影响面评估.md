# 0.4.2 设计与影响面评估（来自 0.4.1 实战会话的三条反馈）

> 来源：会话 `session-75e156fa-c02b-4c52-9a22-84248ceb068e`（在 quantming 项目里实测 0.4.1：
> 54 个月末 × 700 只 × 四因子 `volume_ratio` / `close` / `circ_mv` / `dv_ttm`）。
> 该会话结尾认定「建议反馈给上游」的是三条：**`is_oos` 下界提示**、
> **`double_sort` / `clean` 用法**、**`to_markdown` 可选依赖**。
>
> 本文只做**可修性检验 + 方案设计**，不含实现。

## 1. 可修性检验（逐条实测，先判定"是不是库的问题"）

| # | 反馈 | 检验结论 | 性质 |
|---|---|---|---|
| ① | `is_oos` 样本量下界（≳43 期才跑通） | **成立，而且比"缺提示"严重**：是**单位错配的真 bug** | ✅ 库侧、必修 |
| ② | `double_sort` 需 `forward_return_*`、`clean()` 只能单列 | **成立**，但性质是**报错指错方向**（不是功能缺失） | ✅ 库侧、可修 |
| ③ | `to_markdown()` 需要 `tabulate` | **不成立** —— 库自带渲染，**零 tabulate 依赖** | ❌ 库侧无需修（只需一句文档澄清） |

### ① 实测：`embargo` 数的是"分析日期网格的位置数"，而 `build_report` 用**交易日数**算它

`split_is_oos(dates, …, embargo=N)` 里的 `N` 是**你在 `dates` 里数多少期**；而
`build_report` 的默认值是 `max(horizons) + 1` —— `horizons` 是**交易日数**。
两者在**日频**面板上恰好同量纲，一旦分析是**月末调仓**，就差约 21 倍。

月末 60 期面板实测（0.4.1）：

| horizons | 默认 embargo | 结果 |
|---|---|---|
| `(5,)` | 6 | 跑通，IS=35 / OOS=18 |
| `(21,)` | 22 | 跑通，IS=19 / OOS=18 —— **挖掉了 22 个月末 ≈ 2 年**（本意是 22 个交易日 ≈ 1 个月） |
| `(21, 63)` | 64 | ✗ `split/too_few_periods`：**样本内 0 期** / 样本外 17 期 |
| `(21, 63, 126)` | 127 | ✗ 同上：**样本内 0 期** / 样本外 16 期 |
| 显式 `embargo=1` / `2` | 1 / 2 | 跑通 ✓（用户只能自己绕开默认） |

会话里"≳43 期才跑通"正好对应 `h=21` 那一行：`0.7N − 22 ≥ 8 ⇒ N ≥ 43` ✓ 算式吻合。

**危害**：非日频面板上默认配置**要么过量 purge（样本内被砍掉大半）**、
**要么直接跑不起来**；而"样本内外对照"的全部意义就是那段样本 —— 这比"少个提示"严重。

**可修性**：可修，且修法明确（见 §2）。**根因是 `embargo` 的语义单位**，
不是阈值没写清楚。

### ② 实测：两条报错都指错了方向

| 调用 | 0.4.1 的报错 | 它想说的 |
|---|---|---|
| `double_sort(factor_df, by=…)` | `[group/no_factor]` 缺 `factor` 列；实际列 `['value','size','available_at']` | 真实要求是"输入必须是**含 `forward_return_*`** 的清洗面板"—— 让人去改列名，方向是错的 |
| `clean(multi_factor_df, returns)` | `[clean/ambiguous_factor]` 因子表看不出哪列是因子值（候选 `['roe','mom']`）。修法：命名为 `value` 或 `factor` | 真实约束是"**一次只能一个因子**"；多因子应当逐列跑，或走 `factor_correlation` / `redundancy_check` |

**危害**：不阻断，但会把使用者引到错误的方向（去改列名，而正解是先算收益 / 拆成单因子）。

**可修性**：可修，纯错误信息 + 文档层面，不动数值 ✓。

### ③ 检验结论：**库侧不成立**（这里要纠正那次会话的判断）

证据（0.4.1 源码）：

- `report/__init__.py::_md_table` 是**自写渲染器**（自己拼 `| … |` 与分隔行）；
- 全库 `grep 'to_markdown()'` → **0 处**调用 pandas 的 `DataFrame.to_markdown()`；
- `pyproject.toml` 的依赖只有 `numpy / pandas / scipy`，**没有也不需要 tabulate**。

会话里那条"`to_markdown()` 会报错"，是**同名方法的歧义**：
pandas 的 `DataFrame.to_markdown()` 需要 `tabulate` ✔，而本库的 `Report.to_markdown()`
自带渲染、**不依赖任何可选包** ✔。在装好 `tabulate` 的环境里复测也确认库侧渲染正常。

**所以 ③ 不需要改代码**，只需要一句文档澄清（见 §4）—— 否则会误导使用者去装一个
本库不需要的包。**这条也说明：那次会话的"根因归属"表里有一格判错了。**

## 2. 方案 A：`is_oos` 的 purge 改成**按日历精确剔除**（核心修复）

### 2.1 思路

别再"数期数"，而是**直接回答那个问题**：哪些样本内样本的前向收益窗口碰到了切分日之后？
把它们剔掉 ✓。

```python
# 现状（按位置数）：embargo = max(horizons) + 1  ← 单位是"分析日期网格的位置"
# 改成（按日历算）：IS 只保留 exit_date(t, h) < cut 的样本
```

### 2.2 API 设计（全部是**可选新增**，不改既有签名语义）

```python
split_is_oos(dates, *, ratio=0.7, cut=None, embargo=0, min_periods=8,
             calendar=None, purge_horizons=None, entry_lag=1)
```

- 给了 `calendar` + `purge_horizons` → 走**精确 purge**：
  对每个 IS 候选日期 `t`，算出 `exit = shift_dates(t, entry_lag + max(purge_horizons))`，
  只保留 `exit < cut` 的（返回里多一个 `purged` 计数与 `mode='exact'`）；
- 只给 `embargo` → 保持现在的"按位置数"语义（向后兼容 ✓，文档写明单位是**分析日期期数**，
  不是交易日 ✓ —— 这一点现在写反了）；
- 两个都给 → 报错（避免两种口径打架）。

`build_report(is_oos=…)` 默认改为**传 `calendar` + `max(horizons)`** 走精确 purge ✓；
用户显式给 `embargo=N` 时仍按老口径（尊重显式意图 ✓），并在报告里写明用的是哪种。

### 2.3 两条必须守住的语义

1. **`entry_lag` 要跟着 `ReturnModel` 走**：默认 `entry='next_open'` → lag=1；
   若使用者用 `entry='close'` / `'same_open'`（lag=0），purge 也要跟着变，
   否则又差一天。设计上**从 `model` 里取**，而不是硬编码 1。
2. **`min_periods` 的下界要给出来**：报错信息里直接写
   「按当前 `ratio`/`cut` 与 `horizons`，需要 ≈N 期分析日期（现在 M 期）」，
   并把可用公式写进 docstring：`N ≥ max(min_periods/(1-ratio), min_periods/ratio) + 所需 purge 期数`。

### 2.4 影响面

| 维度 | 评估 |
|---|---|
| 谁受影响 | **只有显式用了 `is_oos=` 的人**（默认 `None` 不触发） |
| 数值变化 | 段边界会移动 → 那两段的 IC/IR/期数会变（**这是修 bug 的必然结果**）✓ |
| 日频面板 | 与旧实现差异应 ≤ 1 期（可 A/B 证明）✓ |
| 非日频面板 | 从"过量 purge / 跑不起来"变为"正确"✓ |
| 版本归属 | `is_oos` 是 0.4.0 新增的可选功能 → 这是它的 bug 修复 → **0.4.2（patch）** |
| 测试 | ① 月末 60 期 + `(21,63,126)` 必须跑通；② **IS 段每个样本的出场日 < 切分日**（按日历验算，不是断言魔数）；③ 日频面板新旧差异 ≤ 1 期；④ `embargo` 与 `purge_horizons` 同时给 → 报错 |

## 3. 方案 B：两条报错改成"指向下一步"

| 位置 | 现在 | 改成 |
|---|---|---|
| `double_sort` / `grouped_ic` 缺 `forward_return_*` | 报 `no_factor`，说"缺 factor 列" | 新增专用规则 `need_forward_returns`，信息里给**两步处方**：`r = forward_returns(px, cal, horizons)` → `cr = clean(factor, r)` → `double_sort(cr.data, by=…)`；并提示"一条龙入口是 `build_report`" |
| `clean` 的 `ambiguous_factor` | 只说"命名为 `value`/`factor`" | 追加一句：**一次只能一个因子**；多因子请逐列调用，比较因子间关系用 `factor_correlation` / `redundancy_check` |

**影响面**：只改错误文本与 docstring ✓ 不动数值 ✓ 不动签名 ✓ → 可进 **0.4.2** ✓。
测试：断言新规则的 `rule` 名与关键短语（避免以后又被改回误导性文案）。

## 4. 方案 C（原③）：**不改代码**，只补一句文档澄清

在 README 的「三分钟上手」与 `docs/输入数据规格.md` 各加一句：

> `Report.to_markdown()` 自带 Markdown 渲染，**不依赖任何可选包**（本库零绘图、零额外渲染依赖）。
> 需要 `tabulate` 的是 **pandas 自己的** `DataFrame.to_markdown()` —— 两者同名但不是一回事。

**影响面**：纯文档 ✓。**收益**：避免使用者为一个本库不需要的包去改环境/改代码。

## 5. 附带建议 D：给报告节次一个**稳定的锚点**（可选，建议一起做）

会话里那条 `upgrade_check.py` 假失败的**库侧根因**：0.4.0 把节次改成自动编号后，
下游只能硬编码 `## 七`，编号一变就假失败 ✗。

设计（很轻）：

```python
SECTION_KEYS = ('verdict', 'health', 'ledger', 'ic', 'newey_west', 'quantile',
                'portfolio', 'stability', 'tail', 'turnover', 'is_oos', 'dropped')

Report.sections() -> list[dict]      # [{'key':'quantile','number':'六','title':'分层'}, …]
```

下游改判 `report.sections()` 里有没有 `key='quantile'` ✓，再也不碰编号 ✓。
**影响面**：纯新增（`__all__` +1 变量/方法）✓ 不动 markdown 输出 ✓ → 可进 **0.4.2** ✓。

## 7. 验收清单（实施后逐条验）

1. 月末 60 期 + `horizons=(21,63,126)` + `is_oos=0.7` → **跑通**，且 IS 段每个样本的出场日
   **严格早于**切分日（按日历验算）；
2. 日频面板：新实现与 0.4.1 的段边界差异 **≤ 1 期**（A/B 证明"只修了单位错配"）；
3. `entry='close'` 的模型 + `is_oos` → purge 少一天（跟 `model` 一致）；
4. `double_sort(原始因子表)` 的报错含"先 `forward_returns` + `clean`"；
   `clean(两列因子)` 的报错含"一次只能一个因子"；
5. `Report.to_markdown()` 在**没装 tabulate** 的环境里正常输出（用 stub 屏蔽 `tabulate` 验证）；
6. 全量测试 + CI 等价环境 + 与 0.4.1 的 A/B（除 `is_oos` 那两段外，**其它数字逐位不变**）。
