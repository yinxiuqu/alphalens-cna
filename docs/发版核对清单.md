# 发版核对清单（发布前 / 发布 / 发布后核对 / 版本字样收尾）

`docs/PyPI发布步骤.md` 讲的是**怎么把 PyPI 打通**（账号、Trusted Publisher，只需做一次）；
本文件解决的是**每次发版别漏项** —— 每条都给了能直接粘的命令与期望值。

> 为什么要单独有这份：0.4.2 的发行物与代码本身没问题，漏的是**发布时的文档收尾**
> （`版本进展.md` / README 的版本字样），事后补了一个纯文档提交才对齐。
> 所以「版本字样收尾」不靠记性，靠清单。

发版时复制一份到提交信息或 issue 里，逐条打勾。

---

## 0. 一句话流程

```
改版本号 + CHANGELOG 提版 + 四处版本字样
        → pytest 全绿 → commit & push → GitHub 建 Release
        → publish.yml 自动构建并发布到 PyPI
        → 发布后核对（Actions / PyPI 版本号 / sha256 / 逐字节一致）
```

**顺序很重要**：`版本字样收尾` 必须在**建 Release 之前**做完并推上去，
否则 README 的旧字样会随这次发行物一起上传到 PyPI（见第 4 节的坑 ①）。

## 1. 发布前（本地）

- [ ] **`pyproject.toml` 的 `version`** 已 bump
      ```bash
      grep -n '^version' pyproject.toml
      ```
- [ ] **`CHANGELOG.md` 提版**：把内容从 `## [Unreleased]` 提为 `## [X.Y.Z] - YYYY-MM-DD`，
      `### 待办` 留在 `[Unreleased]`（照 0.4.0 / 0.4.2 的 `release:` 提交写法）
      ```bash
      grep -n '^## \[' CHANGELOG.md | head -3
      ```
- [ ] **全量 pytest 真的能跑完**（不是"看起来在跑"）
      ```bash
      python -m pytest -q
      # 期望：576 passed（数字变了就同步改 README 防线 5，见第 4 节）
      ```
      > ⚠️ 如果卡住不动、CPU 跑满：**先怀疑新增的报错提示函数互相调用**。
      > 0.4.2 就踩过 —— `split_is_oos` 的 `too_few_periods` 提示函数回头调用公开入口，
      > 公开入口报错时又调它，无限递归，`timeout` 都杀不掉。
      > 报错信息里要算"额外统计量"时，务必抽一个**只算不报错**的内部函数给它调。
- [ ] **三件 CI 等价检查本地过一遍**（可选但便宜）
      ```bash
      bash scripts/ci_local.sh --quick
      ```
- [ ] **两个 run 的期望值**：push 后 `CI`、建 Release 后 `Publish to PyPI`

## 2. 发布

- [ ] `git push origin main`
      > 推不通（挂住 / `GnuTLS recv error (-110)` / `Could not connect`）？**别盲重推**，
      > 直接 `scripts/push_fallback.sh`（按通道依次试），定位与全部备用通道见 **附录 A**。
- [ ] GitHub → Releases → **Draft a new release** → tag `vX.Y.Z` → Publish
      （**不要**本地 `git tag` + `--tags`：本仓库 0.2.0 起各版都直接用 main 发，
       tag 由 GitHub Release 创建；本地 `git tag -l` 只到 v0.1.7 是正常的）
- [ ] 建完立刻看 `Publish to PyPI`：`twine check` 门禁不过会在这步失败，
      **不会**浪费掉版本号

## 3. 发布后核对（不装包）

先跑 ②③（一条命令）：

```bash
V=0.4.2                                    # ← 改成本次版本
echo "--- ② PyPI 版本号与 sha256 ---"
curl -s "https://pypi.org/pypi/alphalens-cna/$V/json" | python -c "
import json,sys
d=json.load(sys.stdin)
print('version =', d['info']['version'])
for f in d['urls']: print(' ', f['filename'], f['digests']['sha256'])"

echo '--- ③ 下载后本地 sha256 对一遍 ---'
# ★ 必须指定官方源：本机 pip 配的是阿里云镜像，同步严重滞后
#   （实测 0.4.2 发布后镜像上还只到 0.3.0，连 0.4.1 都没有）
pip download "alphalens-cna==$V" --no-deps -d /tmp/alc \
    -i https://pypi.org/simple && sha256sum /tmp/alc/*
```

> ⚠️ **镜像滞后**：本机 `pip config` 的 `index-url` 指向 `mirrors.aliyun.com`。
> 核对发行物时一律加 `-i https://pypi.org/simple`，否则会拿到旧版本、
> 或者直接 `No matching distribution found`（镜像还没有这一版）。
> 这跟使用者装包是同一回事 —— README 里已经提醒过国内镜像有新包延迟。

完整清单（①–⑤）：

- [ ] **① Actions 两个 run 都 success** —— `CI`（push）与 `Publish to PyPI`（release）。
      用 API 查比 `git ls-remote` 稳：
      ```bash
      curl -s "https://api.github.com/repos/yinxiuqu/alphalens-cna/actions/runs?per_page=6" \
        | python -c "
      import json,sys
      for r in json.load(sys.stdin)['workflow_runs']:
          print(f\"{r['head_sha'][:7]}  {r['name']:18} {r['event']:8} {r['status']}/{r['conclusion']}\")"
      ```
      > ⚠️ 本机 `git ls-remote` 偶发**卡死不返回**（要 `timeout` 兜底），
      > 核对外部状态一律走 API / `curl`。
- [ ] **② PyPI 上的版本号** = 本次版本
- [ ] **③ 发行物 sha256**：PyPI 记录的与本地 `sha256sum` **完全一致**
- [ ] **④ tag 指向的提交** = **建 Release 时 main 的 HEAD**
      ```bash
      curl -s "https://api.github.com/repos/yinxiuqu/alphalens-cna/git/ref/tags/v$V" \
        | python -c "import json,sys; print(json.load(sys.stdin)['object']['sha'])"
      ```
      > ⚠️ 别拿它跟**当前** `git rev-parse HEAD` 比：发完版之后再补文档提交（0.4.2 的
      > `fcd48e3` 就是）HEAD 会前进，tag 仍指向发布提交 —— **这是正常的**，
      > 不要因为对不上就重新发版。要比的是"当时推上去的那个提交"。
      >
      > 另注：本仓库 **0.2.0 起的 tag 只在远端**（由 GitHub Release 创建），
      > 本地 `git tag -l` 只到 v0.1.7 —— 想本地用 tag 得先 `git fetch --tags`。
      > 所以下面一律用 API 取 SHA。
- [ ] **⑤ 发行物源码 == 发布提交（逐字节）** —— 证明发上去的确实是这一份代码。
      在**仓库目录**里跑（纯 bash，无 heredoc，可直接整段复制）：
      ```bash
      set -euo pipefail
      V=0.4.2
      IDX=https://pypi.org/simple            # ★ 绕开滞后的阿里云镜像
      SHA=$(curl -s "https://api.github.com/repos/yinxiuqu/alphalens-cna/git/ref/tags/v$V" \
            | python -c "import json,sys; print(json.load(sys.stdin)['object']['sha'])")
      rm -rf /tmp/alc && mkdir -p /tmp/alc/x
      pip download "alphalens-cna==$V" --no-deps -d /tmp/alc -i "$IDX"
      (cd /tmp/alc/x && unzip -q ../*.whl)

      bad=0; n=0
      while IFS= read -r f; do
        rel=${f#/tmp/alc/x/}
        a=$(sha256sum "$f" | cut -d' ' -f1)
        b=$(git show "$SHA:$rel" | sha256sum | cut -d' ' -f1)
        n=$((n + 1))
        [ "$a" = "$b" ] || { echo "★ 不一致: $rel"; bad=$((bad + 1)); }
      done < <(find /tmp/alc/x -name '*.py')

      echo "共 $n 个 .py：不同 $bad （0 = 发行物与发布提交逐字节相同）"
      [ "$n" -gt 0 ] && [ "$bad" -eq 0 ]   # ★ 没有这一步，下载失败也会"通过"
      ```
      > ⚠️ 别省掉最后那行断言。第一版这段没有它，`pip download` 失败（镜像滞后）时
      > `find` 一个文件都没找到、循环 0 次、照样打印「不同 0」并 `exit 0` ——
      > **静默假通过**比不检查更危险。`set -euo pipefail` + `n > 0` 才算真过。
- [ ] **安装冒烟**：`pip install "alphalens-cna==$V"` 后 `import alphalens_cna` 正常，
      且本次改动的主要功能真的生效（例：0.4.2 验了精确 purge 的 `mode='exact'`
      与样本内末样本出场日 < 切分日）

## 4. 版本字样收尾（★ 最容易漏）

**必须在建 Release 之前做完并推送**，否则要等下次发版才会刷新。

- [ ] `docs/版本进展.md`：`## 现状` 的「已发布」改成新版本 + `## 版本一览` 加一行
- [ ] `README.md` **三处**：
      - [ ] 安装行的版本号（`pip install alphalens-cna  # PyPI 最新 X.Y.Z`）
      - [ ] `## 状态` 的「当前版本 X.Y.Z」
      - [ ] 防线 5 的测试数（`tests/`（N 个））—— 与第 1 节 pytest 的实际数字一致
- [ ] 自查一次（三条都应命中新版本）：
      ```bash
      grep -n "PyPI 最新\|当前版本\|个）" README.md
      grep -n "已发布\|X\.Y\.Z" docs/版本进展.md
      ```

**两个坑：**

1. **README 是 PyPI 页面的长描述** —— 就算 PyPI 上已经是新版，
   页面正文仍显示**上传那一刻的 README**。字样改晚了不会报错，只会静默不一致。
2. **纯文档收尾不发新版** —— 无需 bump 版本号、无需再建 Release；
   但也不会有新的发行物，PyPI 页面上的 README 仍要等下次发版。这点要在文档里写明，
   免得下次有人以为漏发了。

## 附录 A. 推送 / 同步不通时的备用通道

> 不是理论清单 —— 这是 0.4.2 收尾时撞上的真实故障，每条都标了**实测结论**。
> 当天 `github.com:443` 的 git 传输被反复掐断，而 `api.github.com` 全程正常。

### A.0 先分清是哪一层坏了（30 秒，别一上来就盲重推）

盲重推的代价很高：每次可能白等 135 秒才报 `Could not connect`。从上往下三刀：

```bash
getent hosts github.com                                   # ① DNS
timeout 6 bash -c 'echo > /dev/tcp/github.com/443' \
  && echo TCP-OK || echo TCP-FAIL                         # ② TCP
curl -s -o /dev/null -w 'api=%{http_code}\n' https://api.github.com/   # ③ 对照
```

| 现象 | 判断 | 去哪 |
|---|---|---|
| ① 无输出 | DNS 层 | 换 DNS / 换网络 |
| ② 不通 | 链路层 | 换网络（A.1 通道①也无解） |
| ② 通、git 却**挂住不动**或报 `GnuTLS recv error (-110): TLS 链接非正常地终止` | **TLS/传输层** | A.1 通道①（HTTP/1.1） |
| `api.github.com` 通、`github.com` 不通 | 只有 API 这条路 | A.4 |

> 当天四种报错交替出现，**同一条命令不同次还不一样**：挂住不返回 / TLS 中断 /
> `Could not connect ... after 134833 ms` / 偶尔过一次。所以别用"刚才还行"来判断。

### A.1 通道清单（实测结论）

| # | 通道 | 端点 | 需要什么 | 实测结论 |
|---|---|---|---|---|
| ① | HTTPS + `http.version=HTTP/1.1` | `github.com:443` | 已配好的凭证 | **✓ 首选**（本仓库已设为默认） |
| ② | HTTPS 默认（HTTP/2） | `github.com:443` | 同上 | ✗ 本机被干扰：`ls-remote` rc=124 **挂死** |
| ③ | SSH | `github.com:22` | SSH 密钥 + 加到 GitHub | 端口 ✓ 通，**本机无密钥**（见 A.3） |
| ④ | SSH over 443 | `ssh.github.com:443` | 同上 | 端口 ✓ 通（22 端口被挡时用） |
| ⑤ | GitHub API | `api.github.com:443` | token（`repo` 权限） | **✓ 全程可用**（见 A.4） |
| ⑥ | 代理 | 任意 | 可用代理 | 本机未配；`https_proxy=…` 即可 |
| ⑦ | bundle 中转 | 任意介质 | —— | 兜底中的兜底（见 A.5） |

另外实测：`git -c http.sslBackend=openssl` **没用** —— 报
`remote helper 'https' aborted session`（该后端没编译进去），别在它上面浪费时间。

### A.3 SSH 两条通道（一次性配置，需**你本人**执行）

**沙箱里做不了这步**：`~/.ssh` 不在可写范围，密钥必须你自己生成。
生成 SSH 密钥并登记后，③④ 就是长期最稳的路（不依赖 443 上的 HTTPS 传输）。

```bash
ssh-keygen -t ed25519 -C "alphalens-cna"          # 一路回车即可
cat ~/.ssh/id_ed25519.pub                          # 复制这一行
```

把公钥贴到 <https://github.com/settings/keys> → **New SSH key**。

> ⚠️ 这一步**没法用 API 代劳**：本机 `~/.git-credentials` 里的 token 权限是
> `admin:org, repo, workflow, write:packages` —— 不含 `write:public_key`，
> 加不了 SSH key。只能网页贴。

验证与使用：

```bash
ssh -T git@github.com                              # 期望：Hi yinxiuqu! ...
ssh -T -p 443 git@ssh.github.com                   # 22 被挡时走这条
git push ssh main                                  # 用 22
git push ssh443 main                               # 用 443
```

若希望 `origin` 改用 SSH：`git remote set-url origin git@github.com:yinxiuqu/alphalens-cna.git`

### A.4 API 兜底推（SHA 会变，最后手段）

当 ①②③④ 全不通、只有 `api.github.com` 通时用。原理是把改动拆成
blob → tree（`base_tree`）→ commit（parent=远端 HEAD）→ PATCH ref，四步 API 调用。

```bash
scripts/push_via_api.py            # dry-run：列出待推文件与提交数
scripts/push_via_api.py --apply    # 真推
git fetch origin && git reset --hard origin/main    # ★ 推完必须对齐
```

**代价与前提**：

- 提交由 GitHub 用**当前时间**做 committer，**SHA 与你本地不同**（内容、提交信息、
  parent 都一致）。所以推完要 `git reset --hard origin/<branch>` 对齐 ——
  这也是它只能当最后手段的原因：**能换网络就换网络，换网络不会动 SHA**。
- 只在「远端 HEAD 是本地 HEAD 的祖先」时安全；分叉了脚本会拒绝执行。
- 脚本把 API 生成的提交只当成**一个**提交（把两个 HEAD 之间的全部改动打成一个）。

### A.5 bundle 中转（完全不依赖直连）

```bash
git bundle create /tmp/alc.bundle main --not origin/main   # 只打包未推送的提交
# 把 /tmp/alc.bundle 拷到一台能连 GitHub 的机器，然后：
git fetch /tmp/alc.bundle main:refs/remotes/incoming
git push origin incoming:main                              # 或在那边 push
```

### A.6 三条纪律

1. **不要 `--force` / `--force-with-lease` 硬推** —— 网络问题不是历史问题，
   强推只会把远端搞乱。上面所有通道都无需强推。
2. **不要盲重推** —— 先用 A.0 定位；要重推就用 `scripts/push_fallback.sh`
   （它有端口预探测，不通就跳过，不白等）。
3. **报错里的 `无法在 1000 ms 获得凭证存储锁: 只读文件系统` 是无害的** ——
   沙箱不让写凭证缓存，推送照常成功（`PUSH_EXIT=0` 且远端确实更新了）。别被它带偏。
