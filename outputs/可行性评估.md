# alphalens-cna 可行性评估

> 问题：**工程量很大，设计方案可行吗？**
> 方法：回溯设计 → 盘点规模 → 分级难度 → 切 MVP
> 状态：**评估稿，不动手**

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| **架构可行吗？** | ✅ **可行**。七层是自下而上的依赖，没有循环，每层可独立验证 |
| **一次做完现实吗？** | ❌ **不现实**。40 个模块、7,000–9,000 行，一次做完必然烂尾 |
| **核心部分难吗？** | ✅ **大部分是 routine**。真正难的只有 **5 处**（见 §3） |
| **有沉没资产吗？** | ✅ **有**。本会话已跑通 **1,265 行** 分析代码，是 L3/L4 的雏形 |
| **最大的风险** | ⚠️ **不是技术，是范围**。设计是"终态"，不是"第一步" |

**一句话**：**方案可行，但必须切 MVP——把"能不能用"和"好不好用"分开做。**

## 三、难度分级：真难点只有 5 处

**这是评估里最重要的一节。** 把"看起来难"和"真的难"分开。

### ✅ Routine（占比约 80%，照着规格写就行）

- 预处理五件套（去极值 / 标准化 / 中性化 / 正交化 / 合成）—— 数学简单
- IC / RankIC / ICIR / 换手 / 秩自相关 —— **已有跑通的实现**
- 分层与多空组合 —— 已有
- Fama-MacBeth 两阶段 —— 已有
- 带原因的清洗账 —— 纯记账
- 数据体检、报告输出、适配器 —— 纯工程

### ⚠️ 真难点（5 处，必须专门设计或明确降级）

| # | 难点 | 为什么难 | 建议处置 |
|---|---|---|---|
| **1** | **与 alphalens 1e-10 对拍** | alphalens 有已知怪癖（D1 非日频崩、D2 列名错标、**D9 非日频静默返 NaN**）。**我们不该复刻 bug**，但"1e-10 一致"要求全复刻 | **收口**：限定退化场景 + 只对拍三个核心量（见 §7.1） |
| **2** | **有效样本量估计** | 重叠观测下**学术上没有唯一答案**。本次 91 个月 → 约 7 是个启发式 | **收口**：明确标注"启发式估计"，**给区间不给点估计**，且不作 Verdict 硬门槛 |
| **3** | **Shanken 修正** | 公式容易推错，且与 NW 修正叠加时口径易混 | 后置到 M2，并与 `linearmodels` 交叉验证 |
| **4** | **BHY 实现** | 依赖情形的 FDR 控制，`c(n)=Σ(1/i)`，容易写错 | 用**已知答案测试**锁死（手算 n=4 的 c(n)=2.083，本次已验证） |
| **5** | **"类型上区分 raw/adj"** | **Python 没有强制类型**。设计里说"只允许读 raw_*"，语言层面做不到 | **收口**：改为**校验 + 命名约定 + 单测**，不宣称类型强制 |

> 第 5 条是设计文档里的一处**过度承诺**，应当修正。

## 五、风险清单（按严重度）

| 级别 | 风险 | 缓解 |
|---|---|---|
| 🔴 **高** | **范围爆炸** —— 设计是终态，一次做必然烂尾 | **切 MVP**（§6），每期有独立出口标准 |
| 🔴 **高** | **对拍 1e-10 达不成** —— alphalens 怪癖 vs 我们不复刻 bug | 限定场景 + 只对拍三量（§7.1） |
| 🟡 中 | **数据层慢** —— `stock_day` 按日查 93 秒（无 date 索引） | 本地 parquet 面板缓存（已在用） |
| 🟡 中 | **内存 10GB** —— 大面板吃紧 | 长表 + float32 + 分块；2600×5066 已验证 |
| 🟡 中 | **有效样本量无标准答案** | 标注启发式 + 给区间（§3-2） |
| 🟢 低 | 契约太重不好用 | 提供一行式高层 API，契约在底层强制 |
| 🟢 低 | 复权口径 | **已解决**（退市股核查已完成，三价契约已固化） |
| 🟢 低 | ST / 涨跌停判定 | **已解决**（`execution.py` 可复用 + `limit_status` 语义已破解） |

> **注意**：原本最不确定的两块（复权口径、ST/涨跌停）**在本会话已经解决**。
> 剩下的风险主要是**范围**和**对拍**。

## 六、★ MVP 切分：三个里程碑

**核心原则：把"能不能用"和"好不好用"分开。**

```
M0 能用 ──► M1 可信 ──► M2 完整
（替代 alphalens）（证明自己是对的）（增值功能）
```

### M0 · 可用内核

**目标：能替代 alphalens 做 A 股因子分析，且结论带显著性**

```
contract/{panels, calendar, validate}
engine/{tradability, returns, clean}
analysis/{ic, quantile, portfolio}
inference/{multiplicity, estimate, verdict}
adapters/input/{base, dataframe, parquet}   ← 核心零数据源依赖
report/frames
```
约 **13 个模块 · ~1,800 行**

> **适配器分层**（见总体设计 §3.5）：核心只随包提供 `dataframe`（零依赖）和 `parquet`（公开目录约定）。
> `optional/quantaxis`、`tushare` 等走 extras；**私有数据源写 `examples/` 里的适配器，不进核心包**。

**出口标准（可判定）**：
1. 用本库**复现 `ROE月度调仓分析报告.md` 的每个数字**
2. 输出**带 BHY 校正的 p 值 + `n_trials`**
3. 契约拒绝前视输入（有单测）
4. 清洗账条数对得上（不变量断言）

> **做完 M0 就已经超越 alphalens 了** —— A 股制度正确 + 有显著性检验。

### M1 · 可信内核

**目标：能证明自己没算错**

```
+ analysis/{regression, event}
+ inference/{newey_west, robustness, rank_entropy}
+ health/
+ compat/（限定场景的三量对拍）
```
约 **8 个模块 · ~1,200 行**

**出口标准**：
1. 退化场景下与 alphalens 的 **IC / 分层均值 / 换手** 三量 **1e-10 一致**
2. 已知答案测试通过（3 股 × 2 日手算数据集）
3. 逐条归因：打开每条 A 股规则后，差异全部可解释

### M2 · 完整框架

```
+ preprocess/ 全部（含中性化、对称正交、合成）
+ analysis/{双重排序, diversity}
+ inference/{shanken, effective_n, deflated}
+ ledger/
+ report/markdown
```
约 **18 个模块 · ~2,000 行**

**出口标准**：`pip install alphalens-cna`，CI 全绿，台账可跨项目累积

## 七、建议对设计做 5 处收口

### 7.1 对拍：从"全链路 1e-10"改为"三量 1e-10"

**原文**（§10 防线 4）：
> 退化配置（关闭全部 A 股规则、日频、收盘成交）下与 alphalens **数值一致（容差 1e-10）**

**问题**：alphalens 在非日频下**静默返回 NaN**（D9），复刻它就是复刻 bug。

**改为**：
> 在**日频 + 收盘成交 + 关闭 A 股规则**的退化场景下，
> **IC / 分层均值 / 换手**三个核心量与 alphalens **1e-10 一致**。
> 其余 API 不承诺数值一致（alphalens 有已知缺陷，**明确不复刻**）。

→ 成本大幅下降，信任价值保留。

### 7.2 有效样本量：降级为"启发式估计"

原文把它与 NW / Shanken 并列。**它没有唯一答案**，不应当作精确量。

**改为**：标注为**启发式**，输出**区间**而非点估计，且**不作为 Verdict 的硬门槛**。

### 7.3 契约"类型强制"：改为"校验 + 约定"

原文说"只允许读 `raw_*`"。**Python 做不到语言级强制。**

**改为**：契约校验 + 命名约定 + 单测覆盖，**不宣称类型强制**。

### 7.4 三档 API：M0 只做 L2/L3

L1 一行式（`quick_report`）留到 M2。**先保证显式流水线可用**。

### 7.5 台账：M0 只做 `record()`，完整功能后置

台账是**增量价值**，不影响单次分析的正确性。
M0 只要有最简单的 `record()` 能供给 `n_trials` 即可，查询/审计/跨项目留到 M2。

> 逐条登记，避免"记不清了"。

### ✅ 已定（2026-09-22）

| # | 事项 | 决定 | 影响 |
|---|---|---|---|
| **D1** | **对拍口径** | **收口为「IC / 分层均值 / 换手」三量 1e-10** | 只对拍三个核心量；其余 API 明确**不复刻 alphalens 缺陷**（D1/D2/D9） |
| **D2** | **成交模型默认策略** | **`skip`** | 不可成交样本剔除并计入原因账，报告占比 |
| **D3** | **新股过滤阈值** | **默认剔除上市前 60 个交易日** | 同时使"新股涨跌幅规则"的复杂性变得不必要（60 > 5） |

| **D7** | **适配器分层** | 核心**零数据源依赖**：只随包提供 `dataframe` + `parquet`；公开数据源走 `optional/` + extras；**私有数据源写 `examples/`，不进核心包** | 库里**永不出现任何人的私有目录名**，保证开源可用性 |
| **D4** | **M0/M1/M2 切分** | ✅ **接受，开始执行**（2026-09-22） | 分三期交付；**M0 出口 = 复现月度 ROE 报告 + BHY 校正 p 值** |
| **D8** | **输入规格文档** | **必须写清**：字段名、类型、索引、单位、目录约定、最小示例 | 用户强调项。落点 `docs/输入数据规格.md`，**先于代码写** |

> **D5 的副产品 —— 白捡的防线**：
> 既然 A、B 在收益上应当等价，就可以**互相验证**：
> **同一份数据、两种口径算出的收益必须 1e-10 一致**，不一致即说明复权数据或算法有问题。
> 这条直接并入**六道防线第 3 条（不变量对账）**，成本为零（两种口径本来都要实现）。

## 九、一句话

> **设计没问题，问题在"一次做完"这个念头。**
>

> **M0 约 13 个模块就能交付一个超越 alphalens 的可用内核** ——
> 因为最难的两块（复权口径、ST/涨跌停）**本会话已经解决了**，

>
> 真正的风险只剩两个：**范围**，和**对拍的口径**。两个都有明确解法。
